### 논문에서 IDA를 비교하지 않은 이유

저자들은 §5.1에서 디스어셈블 방식별 대표 도구를 선정했다고 설명합니다. 선형·재귀 탐색에는 Ghidra 11.3.2, superset disassembly에는 DDisasm, 신경망 방식에는 Loadstar를 골랐습니다. §1은 IDA Pro도 표준 형식에서 높은 정확도를 보일 수 있다고 설명합니다. IDA를 따로 제외한 이유는 논문에 기재되지 않았습니다. 표 4의 비교 대상에는 IDA가 없습니다. [논문 §1, §5.1](https://doi.org/10.1145/3830454.3832592)

## 전체 Coreutils 평가

완료한 입력은 **412 / 412개**입니다. 저자가 제공한 GNU Coreutils 9.9의 stripped ELF에 대해 각 바이너리의 지표를 계산한 뒤 같은 가중치로 평균했습니다.

| 빌드 | 완료 / 대상 | 기본 P / R / F1 | 포트 P / R / F1 | F1 상승 / 동일 / 하락 |
| --- | --- | --- | --- | --- |
| arm32-gcc | 102 / 102 | 1.00000 / 0.99999 / 1.00000 | 0.99977 / 1.00000 / 0.99989 | 0 / 48 / 54 |
| arm32-llvm | 104 / 104 | 1.00000 / 0.99998 / 0.99999 | 0.99964 / 0.99998 / 0.99981 | 0 / 40 / 64 |
| mips-gcc | 102 / 102 | 1.00000 / 0.99514 / 0.99756 | 0.99973 / 0.99514 / 0.99743 | 0 / 65 / 37 |
| mips-llvm | 104 / 104 | 1.00000 / 0.99604 / 0.99801 | 0.99997 / 0.99604 / 0.99800 | 1 / 93 / 10 |
| 전체 | 412 / 412 | 1.00000 / 0.99779 / 0.99889 | 0.99978 / 0.99779 / 0.99878 | 1 / 246 / 165 |

측정한 바이너리 전체에서 정답 코드 바이트 수의 적용 후 변화량은 **+16**입니다.

측정한 바이너리 전체에서 오탐 바이트 수의 적용 후 변화량은 **+3,848**입니다.

F1 변화의 양 끝에 있는 입력은 다음과 같습니다.

| 빌드 / 프로그램 | 기본 F1 | 포트 F1 | 정답 코드 변화 (바이트) | 오탐 변화 (바이트) |
| --- | --- | --- | --- | --- |
| mips-llvm / expr | 0.999505 | 0.999516 | +4 | +0 |
| mips-gcc / false | 0.996794 | 0.995973 | +0 | +36 |

Vanilla IDA 결과는 비어 있는 IDAUSR 프로필에서 포트를 로드하지 않고 독립 검산했습니다. 이 검산은 IDA의 명령어 시작 주소와 항목 크기를 직접 순회합니다. 현재 비교 가능한 412개 중 TP·FP·FN이 모두 일치한 입력은 412개입니다. [독립 검산 결과](clean-baseline.json)

## 실험 방법

- 공식 TOML에서 네 Coreutils 빌드의 입력 이름, 기준 주소, 최대 반복 수와 에폭 수를 읽었습니다. 각 stripped ELF의 복사본으로 새 IDB를 열어 자동 분석을 마치고 기본 상태를 측정했습니다. 같은 IDB에 포트를 적용하고 마지막 재분석이 끝난 뒤 다시 채점했습니다.
- 모델은 바이너리별로 새로 학습했습니다. seed 42, 500에폭, 최대 5회, 임계값 0.50을 사용했습니다. 저자 평가 코드의 적용 범위에 맞춰 실행 가능한 세그먼트의 미정의 영역과 기존 데이터 항목을 대상으로 했습니다. 포트의 기본 미리보기에서는 기존 데이터가 제외됩니다.
- CSV의 ground_truth가 0이면 해당 주소부터 4바이트가 정답 코드입니다. 정답은 모델 학습과 IDB 적용이 끝난 후 채점기에만 전달했습니다. ELF .text의 파일 오프셋으로 IDA 주소를 대응시키고, 각 양성 행의 원시 4바이트와 IDB 값을 대조했습니다. 일치 개수, SHA-256, 장치, 패스별 학습 손실과 경과 시간은 개별 JSON에 있습니다.
- 주 지표는 초기화된 일반 세그먼트에서 IDA가 코드로 표시한 모든 바이트와 정답 집합의 차이로 계산했습니다. 정답 집합 밖의 코드도 FP에 포함했습니다. 보조 지표는 공식 NSDA 함수처럼 블록 시작부터 4바이트 간격으로 검사하고 데이터·미정의 블록에서 검사한 정답 위치를 FN으로 셉니다. 두 채점기의 분모는 다를 수 있습니다.
- 비교 환경은 Windows, IDA Pro 9.4 (260714), Python 3.14.7, PyTorch 2.15.0 CPU, LTNtorch 1.0.2입니다. 저자 공개값과 로컬 Ghidra 재실행값은 각 표에 표시했습니다. 저자의 Ubuntu/Ghidra 11.3.2/CUDA 환경과 하드웨어가 달라 실행 시간은 직접 비교하기 어렵습니다.

## 재실행

프로젝트 루트에서 다음과 같이 두 저장소의 평가 자료를 준비합니다.

```powershell
git clone https://github.com/gdjs2/NSDA.git evaluation/upstream/NSDA
git -C evaluation/upstream/NSDA checkout 21814efab2155dab48c74eb06e43deb6b24a4970
git clone https://github.com/gdjs2/NSDA-coreutils-dataset.git evaluation/upstream/coreutils
git -C evaluation/upstream/coreutils checkout 9962bca2c5073e4ddac09a7941479f526597c36d
```

IDA의 idalib를 활성화한 Python으로 프로젝트 루트에서 실행합니다. 학습 워커는 프로젝트의 .venv를 사용합니다.

```powershell
python -X utf8 -u evaluation/benchmark.py
python -X utf8 -u evaluation/benchmark.py --config evaluation/upstream/NSDA/configs/main.toml --output evaluation/full-results --resume
python evaluation/report.py
```

원시 측정값은 [데모 결과](results/)와 [전체 평가 결과](full-results/)에 바이너리별로 저장합니다. 전체 평가의 --build 옵션으로 하나의 아키텍처·컴파일러 조합을 지정할 수 있습니다.

Ghidra 비교를 재실행할 때는 프로젝트 가상 환경에 `pyghidra==2.2.0 rich==14.2.0 loguru==0.7.3`을 추가합니다. 11.3.2는 `.venv\Scripts\python.exe evaluation/ghidra_demo.py --ghidra <Ghidra 설치 폴더>`로 실행합니다. 12.x는 해당 배포본의 Ghidra/Features/PyGhidra/pypkg/dist 안에 있는 pyghidra 휠을 별도 폴더에 풀고 `--pyghidra-path <휠을 푼 폴더>`를 추가합니다. IDA 독립 검산은 `python evaluation/clean_baseline.py --ida-dir <IDA 설치 폴더>`로 실행합니다.

세 버전의 데모 측정값이 준비되면 Matplotlib을 설치한 Python에서 `python evaluation/publish_results.py`를 실행해 GitHub README의 결과 표와 그래프를 갱신합니다.
